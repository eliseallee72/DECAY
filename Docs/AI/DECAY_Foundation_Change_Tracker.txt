DECAY UNITY FOUNDATION CHANGE TRACKER
Last updated: 2026-08-16

PURPOSE
This file travels with the Unity rebuild and records architecture changes that remove or supersede earlier foundation behavior, plus integration rules future steps must preserve. Update it when a later step changes an earlier public type, ownership rule, test assumption, or migration requirement.

STEP 1 REVISION - CHANGES MADE

1. DICE LOCATION AUTHORITY REMOVED FROM DiceRuntimeState
REMOVED:
- DiceLocation and DiceLocationKind.
- DiceRuntimeState.Location.
- MoveToBoard, MoveToBattleInventory, and MarkPending.

REPLACEMENT / FUTURE OWNER:
- BoardState will own board slot occupancy.
- BattleInventoryState will own battle-inventory membership.
- DiceRuntimeState retains only dice-local battle facts such as IsDecayedForCurrentGame.
- Interaction availability is determined by Gates from authoritative state; do not recreate an Unavailable location enum.

TESTS CHANGED:
- Tests that required DiceRuntimeState to reject opposing-side movement were removed because movement validation belongs to the future Board request/gate/controller path.
- Tests no longer assert that DECAYED is a DiceLocationKind.

2. SLOT IDENTITY AND OPPOSING PAIRS CHANGED
CHANGED:
- SlotId.Index -> SlotId.Number (public logical numbers remain 1 through 6).
- Serialized backing field _index -> _number with FormerlySerializedAs for safety.
- SlotId no longer implements IComparable and no longer supplies a generic gameplay ordering.
- FirstSlotIndex / LastSlotIndex -> FirstSlotNumber / LastSlotNumber.

ADDED:
- SlotPairId explicitly represents the opposing Enemy + Player slots with the same Number.
- SlotIndexConverter is the single one-based Slot Number <-> zero-based storage-index conversion path.

FUTURE RULE:
- DecayResolver must iterate numbered SlotPairId values from 1 through 6 and resolve both sides of each numbered pair as one resolution step.
- Do not implement Decay as independently ordered 1E -> 1P -> 2E -> 2P operations.
- Do not assume the Decay ordering automatically applies to every future dice effect. A process owns its own ordering rule.

3. ROLL VALUE IS NOW A HARD 1-6 INVARIANT
ADDED / CHANGED:
- BattleRules.MinimumRollValue = 1 and MaximumRollValue = 6.
- RollValueRules centralizes validation.
- DiceFaceDefinition uses Inspector Range(1,6) and rejects invalid authored values.
- DiceFaceSeed rejects invalid values.
- DiceRuntimeSeed validates face roll values.
- DiceFaceRuntimeState.SetRollValue rejects values outside 1-6.

FUTURE RULE:
- Effects may mutate ROLL VALUE only to another value from 1 through 6.
- Values above/below this range belong in SCORE VALUE or another explicitly designed value, never ROLL VALUE.

4. EFFECT RUNTIME IDENTITY CHANGED
CHANGED:
- IEffectRuntimeState now exposes both EffectInstanceId InstanceId and EffectId EffectId.
- Shared EffectRuntimeStateCollection keys runtime effect-state storage by EffectInstanceId, not EffectId; DiceRuntimeState uses this shared implementation and future charm/battle owners may reuse it.
- Multiple runtime occurrences with the same EffectId are explicitly allowed.
- Duplicate EffectInstanceId on one dice is rejected.

WHY:
Existing planned dice/charms contain repeated triggers, persistent bonuses, and effects that can be supplied by multiple sources. EffectId identifies authored behavior; it cannot safely identify one runtime occurrence.

FUTURE RULE:
- The effect executor/factory must assign battle-runtime unique EffectInstanceId values for stateful runtime occurrences. EffectInstanceId is not permanent content/save identity.
- Reuse EffectRuntimeStateCollection rather than creating parallel registration rules for dice, charms, or other effect owners.
- Concrete effect context/state must preserve whatever source information that effect needs (dice, face, charm, trigger, target, etc.).
- Do not merge runtime states only because EffectId matches.
- Exact stacking/source semantics remain effect-specific and should be approved when each effect family is implemented.

5. CONTENT IDS NOW ENFORCE STABLE CATEGORY FORMAT
CHANGED:
- DiceId requires dice.name.
- EffectId requires effect.name.
- DiceTagId requires tag.name.
- Names are lowercase; the name portion uses lowercase letters, numbers, and underscores.
- Constructor input is trimmed; serialized invalid forms fail IsValid/TryValidate.
- Previous test IDs such as neutral-d6 and starter were replaced by dice.neutral_d6 and tag.starter.

FILE ORGANIZATION:
- Former ContentIds.cs was split so DiceId, OwnedDiceId, EffectId, DiceTagId, and ContentIdValidator each have a focused file.

6. DEFINITION GRAPH VALIDATION STRENGTHENED
CHANGED:
- DiceDefinition and DiceFaceDefinition now call EffectDefinition.TryValidate instead of checking only for a non-empty EffectId.
- DiceRuntimeSeed also recursively validates referenced effect definitions.
- Duplicate authored EffectId references remain rejected within one dice-level list or one face-level list; this does NOT prevent multiple runtime occurrences.

7. BATTLE PHASE PROGRESSION CHANGED
ADDED:
- BattlePhaseTransitionValidator.

CHANGED:
- Tests no longer use numeric enum comparisons to prove process order.
- BattlePhase numeric values are serialization identities only.

FUTURE RULE:
- BattlePhaseController must ask BattlePhaseTransitionValidator before authoritative phase changes.
- Never use CurrentPhase++, enum arithmetic, or numeric ordering as battle-flow authority.
- Current explicit branches include RoundEnd -> Setup/GameEnd and GameEnd -> Setup/BattleEnd.

8. BATTLE HISTORY FOUNDATION ADDED
ADDED:
- BattleFact base with one-time assigned SequenceNumber.
- BattleHistory records facts in resolved order and assigns monotonic sequence numbers.

FUTURE RULE:
- Add concrete Facts only as their systems are implemented (DiceRolledFact, DiceMovedFact, SaveCreatedFact, etc.).
- Each concrete Fact must contain the stable identities and battle/game/round/side/slot/source/target/value context needed to understand that fact.
- BattleHistory records completed results; it never becomes current gameplay authority.

9. CONFIGURATION DEFAULT SOURCE CLEANUP
CHANGED:
- Removed BattleRules.DefaultGamesPerBattle, DefaultRoundsPerGame, and DefaultBattleInventoryCapacity.
- BattleConfig remains the editor-authored configured source for games/rounds/capacity; its field initializers are creation defaults, not a second runtime rule source.
- Default asset names now move toward the documented prefixes (for example conf_BATTLE_New, def_DICE_New, catalog_DICE).

10. RUNTIME SEED FILE / PERSISTENCE BOUNDARY
CHANGED:
- DiceFaceSeed moved into its own file.
- DiceRuntimeSeed is explicitly documented as runtime construction data.

FUTURE RULE:
- Do not serialize DiceRuntimeSeed as save data because it contains EffectDefinition Unity object references.
- Save data must use stable IDs and explicit serializable values, then resolve definitions through catalogs/repositories when loading.

11. TESTS THAT WERE INTENTIONALLY REWRITTEN
REMOVED/SUPERSEDED TEST ASSUMPTIONS:
- DiceRuntimeState owns board location.
- DECAYED maps to DiceLocationKind.Unavailable.
- DiceRuntimeState itself validates board-side movement.
- SlotId.Index is the public slot identity.
- BattlePhase ordinal values define legal transition order.
- Content IDs may be arbitrary strings such as neutral-d6.

ADDED TEST COVERAGE:
- SlotPairId opposing-pair identity.
- Shared slot storage-index conversion.
- Default SlotId invalidity.
- Explicit BattlePhaseTransitionValidator paths and rejected skips.
- Authored, seeded, and runtime ROLL VALUE 1-6 enforcement.
- Multiple runtime occurrences of one EffectId with distinct EffectInstanceId values.
- Duplicate effect-instance rejection.
- Recursive EffectDefinition validation.
- BattleHistory monotonic sequence assignment and one-time recording.

OPEN / DEFERRED DECISIONS TO KEEP VISIBLE
A. GAMEMAKER OWNED DICE ID 0
The GameMaker reference may contain permanent dice IDs beginning at 0, while Unity OwnedDiceId currently requires positive values (>0). Before save migration/import is implemented, explicitly decide whether legacy ID 0 must be supported or remapped. Do not silently change persistent identity.

B. EFFECT SOURCE AND STACKING SEMANTICS
EffectInstanceId now allows repeated runtime occurrences, but concrete source/stacking rules are intentionally NOT generalized yet. Resolve them by effect family when implementing effects; preserve source identity when needed.

C. PROCESS-SPECIFIC ORDERING
Decay pair ordering is confirmed: numbered opposing pairs 1 through 6, both sides in each pair as one resolution step. Scoring/effect ordering may require more specific rules later. Do not manufacture one universal ordering abstraction.

D. UNITY VALIDATION
This revision was produced without a connected Unity Editor. Static code/reference validation can be done here, but Unity 6000.5.8f1 compilation and EditMode Test Runner results must be checked locally after import.


STEP 2 FIRST PASS - AUTHORITATIVE BATTLE / BOARD / INVENTORY STATE
Last updated: 2026-08-15
Baseline: GitHub branch step-1 (validated locally by Elise before this pass)

12. BATTLESTATE NOW OWNS CURRENT PHASE / GAME / ROUND
ADDED:
- BattleState snapshots the configured GamesPerBattle and RoundsPerGame and owns CurrentGameNumber, CurrentRoundNumber, and CurrentPhase.
- BattlePhaseController accepts PhaseChangeRequest, checks BattlePhaseTransitionValidator plus GameEndCondition/configured game limits, executes an approved AdvancePhaseCommand, and records PhaseChangedFact in BattleHistory.
- RoundEnd -> Setup increments the round only when another configured round exists AND neither side is fully Broken.
- RoundEnd -> GameEnd is approved only when GameEndCondition is met: the configured round cap has been reached OR every Player slot is Broken OR every Enemy slot is Broken.
- GameEnd -> Setup increments the game and resets the round number to 1 only when another configured game remains.
- GameEnd -> BattleEnd is permitted only after the configured final game.

PRESERVE:
- Battle phase transitions never use enum arithmetic or CurrentPhase++.
- BattlePhaseTransitionValidator remains the structural transition authority. BattlePhaseController adds progression/configuration constraints around it.
- Presentation (hourglass, hand, animations) must observe these completed changes; it must not set BattleState directly.

DEFERRED:
- Phase transition currently changes battle counters/state only. Round cleanup, GameEnd board reset, DECAYED dice repopulation, score transfer/reset, and presentation sequencing require their own explicit lifecycle/process orchestration and MUST NOT be silently hidden inside BattleState.

13. BATTLE FACT CONTEXT ADDED
ADDED:
- BattleFactContext snapshots GameNumber, RoundNumber, and BattlePhase for historical Facts.
- BattleState exposes CurrentFactContext as a snapshot; BattleState itself remains current authority.
- PhaseChangedFact stores both PreviousContext and CurrentContext so GameEnd -> Setup and RoundEnd -> Setup are historically unambiguous.
- Board/inventory/slot Facts store the context in which their completed change occurred.

PRESERVE:
- BattleHistory is historical only. Never reconstruct current phase, location, slot condition, or dice state by replaying/searching history during normal gameplay.
- Non-phase Commands receive BattleState and snapshot BattleState.CurrentFactContext at Execute time. Callers do not supply arbitrary BattleFactContext values.

14. BOARDSTATE / SLOTSTATE NOW OWN BOARD OCCUPANCY
ADDED:
- BoardState creates exactly 12 authoritative SlotState objects: 1E..6E and 1P..6P.
- SlotState owns SlotCondition and the optional occupying DiceInstanceId for its SlotId.
- BoardState is the authoritative answer for whether a dice is on the board and which slot contains it.
- BoardState does not maintain a second reverse-location cache; TryGetSlotOfDice derives the answer from authoritative slot occupancy to prevent competing copies.
- BoardState reports broken-slot counts / all-slots-broken per Side.

INVARIANTS:
- A DiceInstanceId may not occupy two board slots.
- Placement requires an empty Unbroken slot.
- Board movement and board-board swaps cannot cross Side.
- Board movement requires both the source and destination slots to be Unbroken.
- A slot cannot become Broken while it still contains a dice. Decay/cleanup must remove or return the dice first, then break the slot.
- SetSlotConditionCommand rejects a no-op condition assignment because a Fact must represent a completed state change.

DEFERRED:
- SlotCondition transitions beyond these structural invariants remain process-specific. Do not invent one universal Unbroken/Unstable/Broken transition graph before Decay/Score cleanup is implemented.
- The rule "an unbroken slot opposing a broken slot becomes unstable" belongs to the appropriate resolver/cleanup process; BoardState does not auto-derive it from presentation or polling.

15. BATTLEINVENTORYSTATE NOW OWNS BATTLE INVENTORY MEMBERSHIP
ADDED:
- BattleInventoryState tracks all DiceRuntimeState objects selected for the battle and separately owns which tracked dice are currently members of each Side's Battle Inventory.
- Capacity is enforced per Side across the full selected battle roster, including dice currently on the board or DECAYED for the game. This matches the rule that a side can use at most the configured battle-inventory count for that battle.
- A tracked dice can remain in BattleInventoryState while not being a current inventory member (for example while on the board or later while DECAYED).
- DECAYED dice are rejected by BattleInventoryState itself as current inventory members; this is an owner-level invariant, not merely a placement Gate.
- Player battle roster construction rejects duplicate SourceOwnedDiceId values so one permanently owned dice cannot appear as two runtime player dice in the same battle.
- InventoryDiceIds returns a read-only view; outside code cannot mutate membership by downcasting the exposed collection.

PRESERVE:
- Removing a dice from inventory membership does not delete/reset its DiceRuntimeState.
- Returning an unstable/surviving dice to inventory preserves battle-local score/effect/face changes unless a specific rule says to reset them.
- DECAYED is not an inventory location enum. A DECAYED dice remains tracked and is unavailable for the rest of that game; future Decay/GameEnd orchestration controls when it is absent/repopulated.

DEFERRED:
- Concrete DECAY removal/repopulation commands are intentionally not implemented in this pass; they belong with DecayResolver and GameEnd cleanup so their reset semantics are applied in the correct order.

16. GLOBALINVENTORYSTATE ADDED AS PERMANENT IN-MEMORY SOURCE
ADDED:
- GlobalDiceState pairs permanent OwnedDiceId with the immutable runtime-construction seed used to create battle copies.
- GlobalInventoryState resolves GlobalDiceState by OwnedDiceId and exposes ordered owned IDs through a read-only view.
- A battle DiceRuntimeState created from Global Inventory is an independent runtime copy; battle mutation does not modify Global Inventory data.
- DiceRuntimeSeed and DiceFaceSeed collection views were hardened to ReadOnlyCollection so Global Inventory cannot be mutated by casting their IReadOnlyList properties back to List.

PRESERVE:
- DiceRuntimeSeed remains runtime construction data, NOT SaveData. It may reference EffectDefinition Unity objects.
- Persistent saves must store stable IDs and serializable values and resolve definitions when loading.

DEFERRED:
- Permanent acquisition/removal/upgrades, saving/loading, and commit-back rules are not implemented yet.
- GameEnd repopulation of DECAYED player dice must create/reset battle state from Global Inventory at the correct process boundary.
- GameMaker OwnedDiceId 0 migration remains unresolved (see open decision A).

17. APPROVED BOARD / INVENTORY COMMAND PRIMITIVES ADDED
ADDED:
- PlaceDiceOnBoardCommand: Battle Inventory -> empty Unbroken own-side slot.
- ReturnDiceToInventoryCommand: board -> own-side Battle Inventory without resetting the dice.
- MoveDiceOnBoardCommand: occupied Unbroken slot -> empty Unbroken slot on same Side.
- SwapBoardDiceCommand: two occupied Unbroken slots exchange dice on same Side.
- SwapBoardWithInventoryCommand: atomic Setup-style exchange between one occupied board slot and one same-side Battle Inventory dice.
- SetSlotConditionCommand: approved structural slot-condition change.
- Commands are one-shot and return concrete Facts describing completed changes.
- Board/inventory membership transfer is centralized in BoardInventoryTransferExecutor. It validates both authoritative owners before mutation, then performs the synchronous transfer in one shared path instead of duplicating removal/insertion/rollback code across Commands.
- ReturnDiceToInventoryCommand supports Unstable-slot ejection: the same DiceRuntimeState returns to Battle Inventory without reset and retains battle-local score/effect/face changes. DECAYED dice are rejected from this path.

IMPORTANT BOUNDARY:
- These Commands are approved-operation primitives, NOT permission APIs for views/input.
- Player/AI/tutorial code must not construct gameplay meaning from transforms and must not bypass future Requests/Gates to call state mutation directly.
- Defensive invariant checks in Commands/State protect data consistency; future Gates own user-facing permission/denial logic.

18. SETUP SWAP AND REPOSITION ARE KEPT DISTINCT
CONFIRMED IN FOUNDATION:
- Setup needs the ability to exchange a board dice with a Battle Inventory dice; SwapBoardWithInventoryCommand provides the atomic state operation.
- Reposition is board-only. MoveDiceOnBoardCommand / SwapBoardDiceCommand never put dice into Battle Inventory.

DEFERRED:
- Phase-specific permission is NOT hardcoded into these Commands. Step 3 should route movement through MoveDiceRequest + narrow Gates so Setup and PlayerReposition can approve different destination/movement operations from authoritative BattleState/BoardState/BattleInventoryState.

19. REQUEST/GATE MOVEMENT FLOW INTENTIONALLY DEFERRED TO NEXT PASS
NOT YET IMPLEMENTED:
- MoveDiceRequest / movement intent variants.
- PhaseGate, ownership/control Gate, source-membership Gate, destination Gate, processing Gate, tutorial restriction Gate, and blocking-operation Gate.
- Player drag/click adapters and enemy movement adapters.
- Presentation movement/animation completion.

REASON:
Step 2 establishes authoritative state and atomic Commands first. This prevents the input/view layer from becoming a competing owner while the permission model is still being implemented.

STEP 2 SECOND PASS - UNITY DOC + CARDHOUSE + SPIRE-CODEX ARCHITECTURE AUDIT
Last updated: 2026-08-15
Source package: DECAY_Step2_First_Pass(2).zip

23. GAME-END CONDITION IS NOW STATE-DRIVEN
CHANGED:
- Added GameEndCondition, which reads BattleState and BoardState without becoming an owner of either.
- A game must end after scoring when ANY of these is true:
  1. CurrentRoundNumber has reached RoundsPerGame.
  2. all Player slots are Broken.
  3. all Enemy slots are Broken.
- RoundEnd -> Setup is denied when GameEndCondition is met.
- RoundEnd -> GameEnd is denied when GameEndCondition is NOT met.
- BattlePhaseTransitionValidator still owns structural phase edges; GameEndCondition supplies gameplay-state permission for the RoundEnd branch.

WHY:
The caller must not choose whether a game ended when authoritative BattleState/BoardState can answer that question.

24. DECAYED DICE ARE EXCLUDED FROM CURRENT BATTLE INVENTORY BY THE OWNER
CHANGED:
- BattleInventoryState.ReturnToInventory rejects IsDecayedForCurrentGame.
- BattleInventoryState construction rejects a DECAYED dice as an initial current inventory member.
- DECAYED dice may remain tracked by BattleInventoryState while outside current inventory membership.

CONFIRMED RULE:
- DECAYED dice do not return to current Battle Inventory during the game.
- They are repopulated/reset when a new game begins from the appropriate authoritative source. For player-owned dice this source is GlobalInventoryState.
- The complete GameEnd/new-game repopulation process remains an explicit lifecycle operation to implement with the relevant resolver/cleanup layer; do not hide it inside ReturnToInventory or BattleState.
- Do not wire GameEnd -> Setup as a complete player-facing new-game transition until that lifecycle operation also resets per-game board/inventory state in the documented order.

25. UNSTABLE-SLOT EJECTION PRESERVES BATTLE RUNTIME STATE
CONFIRMED:
- A dice ejected when an Unstable slot breaks is NOT DECAYED.
- It returns to Battle Inventory as the same DiceRuntimeState.
- Its battle-local score/effect/face mutations are preserved.
- The slot can then transition from Unstable to Broken after the dice has been removed.
- Tests cover this exact path.

26. PLAYER PERMANENT IDENTITY CANNOT BE DUPLICATED IN ONE BATTLE
CHANGED:
- BattleInventoryState rejects two Player DiceRuntimeState objects with the same SourceOwnedDiceId even when their DiceInstanceId values differ.
- DiceInstanceId remains battle-runtime identity; SourceOwnedDiceId remains permanent player-owned identity.

WHY:
One permanently owned player dice must not accidentally enter a battle more than once through duplicate runtime instances.

27. CROSS-OWNER BOARD/INVENTORY TRANSFERS ARE CENTRALIZED
ADDED:
- BoardInventoryTransferExecutor is an internal coordination layer shared by:
  - PlaceDiceOnBoardCommand
  - ReturnDiceToInventoryCommand
  - SwapBoardWithInventoryCommand

BOUNDARY:
- The executor does NOT own dice location and stores no parallel location state.
- BoardState remains authoritative for board occupancy.
- BattleInventoryState remains authoritative for current Battle Inventory membership.
- The executor validates both owners before the first mutation and then performs the synchronous transfer.
- Board-only MoveDiceOnBoardCommand and SwapBoardDiceCommand remain BoardState operations and do not go through this executor.

REFERENCE RATIONALE:
- CardHouse CardGroup demonstrates the useful principle that membership transfer should have one central path instead of each caller independently reproducing remove/add behavior.
- DECAY intentionally does NOT copy CardHouse's duplicated Card.Group/MountedCards authority, public mutable lists, singleton communication, or presentation-coupled membership behavior.

28. FACT CONTEXT NOW COMES FROM AUTHORITATIVE BATTLESTATE AT EXECUTION
CHANGED:
- Board/inventory/slot Commands no longer accept caller-created BattleFactContext.
- They receive BattleState and snapshot CurrentFactContext when Execute begins.
- Tests prove a Command created in one phase records the phase that is authoritative when the Command actually executes.

WHY:
Historical Facts cannot claim an incorrect game/round/phase because a caller supplied a stale or fabricated context.

FUTURE:
If Facts later need WHY an operation happened (player drag, enemy plan, tutorial force, Unstable cleanup, effect, etc.), add a separate typed source/reason concept. Do not overload BattleFactContext with causality.

29. INVENTORY ORDER IS NON-AUTHORITATIVE
CONFIRMED / DEFERRED:
- ReturnToInventory currently appends to the side's inventory list.
- This is acceptable for now and may change after drawer/carousel playtesting.
- Gameplay rules MUST NOT depend on Battle Inventory list order unless an explicit future rule says otherwise.
- Presentation/layout may choose a different visual order without changing membership authority.

REFERENCE RATIONALE:
CardHouse usefully separates group membership from CardGroupSettings layout/arrangement. DECAY should preserve the same conceptual separation while using its own cleaner state model.

30. SPIRE-CODEX REFERENCE INTERPRETATION PRESERVED
REFERENCE NOTE:
- spire-codex is a reverse-engineered/decompiled structural reference. Its README documents extraction of the game's C#/.NET DLL into readable model files and parsing of model/state/command patterns.
- It is NOT treated as the original development repository or as code to copy.

USEFUL PATTERNS RETAINED FOR DECAY:
- authored/model identity separate from runtime dynamic values.
- explicit state-machine/process structure.
- command-shaped gameplay actions with typed source/target/value context.
- explicit stack/runtime state distinctions for effect-like systems.

DECAY-SPECIFIC RESULT:
- Keep DiceDefinition / GlobalInventoryState / DiceRuntimeState separated.
- Keep EffectId / EffectInstanceId separated.
- Keep explicit BattleState/BoardState/BattleInventoryState authority.
- Borrow clarity of commands/context/state machines without reproducing Spire implementation details one-to-one.

STEP 3 FIRST PASS - MOVEMENT REQUEST / GATE PERMISSION PATH
Last updated: 2026-08-16
Baseline: GitHub branch step2, tree 1e8fa9180fa6c9812f4b3cf7cb62b7a6f62b0b90. Elise validated the Step 2 baseline locally with 102/102 EditMode tests green and successful Play Mode startup before this pass.

33. MOVEDICE REQUESTS DO NOT CARRY AUTHORITATIVE SOURCE LOCATION
ADDED:
- MoveDiceRequest identifies the ActingSide, DiceInstanceId, and requested MoveDiceTarget only.
- MoveDiceTarget is either one Board SlotId or Battle Inventory.
- The request does NOT state whether the dice currently comes from BoardState or BattleInventoryState.
- MoveDiceGateContext resolves the current source from authoritative BoardState/BattleInventoryState at request-evaluation time.

WHY:
A view, AI planner, tutorial, or developer tool may ask for a move, but it must not be able to manufacture stale/false source state. This preserves the Request -> Gate -> Command boundary in DECAY unity update.txt and avoids recreating DiceRuntimeState.Location.

34. ONE MOVEMENT CONTROLLER NOW OWNS THE PERMISSION ROUTE
ADDED:
- MoveDiceController.RequestMove is the single plain-C# entry point for movement permission in this pass.
- It builds authoritative MoveDiceGateContext, evaluates the movement Gate collection, executes exactly one matching Step 2 Command when approved, records the returned BattleFact, and returns MoveDiceResult.
- A rejected request returns a typed MoveDiceDenialReason, changes no authoritative state, and records no Fact.

APPROVED COMMAND MAPPING:
- Battle Inventory -> empty Board slot: PlaceDiceOnBoardCommand.
- Battle Inventory -> occupied own Board slot: SwapBoardWithInventoryCommand.
- Board -> Battle Inventory: ReturnDiceToInventoryCommand.
- Board -> empty own Board slot: MoveDiceOnBoardCommand.
- Board -> occupied own Board slot: SwapBoardDiceCommand.

PRESERVE:
- Commands remain approved-operation primitives; they do not become phase permission APIs.
- BoardState remains occupancy authority; BattleInventoryState remains inventory-membership authority.
- Views/AI/tutorial code must submit requests rather than duplicate these checks or call movement Commands directly.

35. CORE MOVEMENT GATES ARE NARROW AND READ-ONLY
ADDED CORE GATES:
- MovementBattleGate: whether the battle is already complete and therefore blocks normal movement requests.
- MovementControlGate: whether the requested tracked dice is controlled by the acting side.
- MovementSourceGate: DECAYED/unavailable dice, exactly-one-source invariant, source slot condition, and source-side consistency.
- MovementPhaseGate: Setup versus EnemyReposition versus PlayerReposition permission.
- MovementDestinationGate: own-side destination, no-op rejection, Unbroken slot requirement, and occupied-destination runtime-state consistency.
- MoveDiceGateCollection stops at the first specific denial.

PRESERVE:
- Gates read authoritative state and never mutate it.
- Gate denial reasons are gameplay/referee results, not presentation state.
- Defensive invariants in State/Commands still remain even after a Gate approves a request.

36. SETUP AND REPOSITION MOVEMENT RULES ARE NOW EXPLICITLY ENFORCED
SETUP:
