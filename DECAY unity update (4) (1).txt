DECAY UNITY NAMING


GENERAL
- Project/title spelling: DECAY.
- C# namespace root: Decay.
- C# types and public members: PascalCase.
- Private fields: _camelCase.
- Method parameters and local variables: camelCase.
- Interfaces: IName, such as IRandomSource or IBattleCommand.
- Booleans begin with Is, Has, Can, Should, or Was when possible.
- Events describe completed facts in past tense or established state: DiceMoved, PhaseChanged, SlotBroken.
- Avoid unexplained abbreviations.
- Use Dice rather than Die always for clarity.


RESPONSIBILITY SUFFIXES
- Definition: immutable authored content, usually a ScriptableObject.
- Config: shared tuning or setup values.
- State: authoritative mutable runtime data with no presentation.
- Controller: accepts requests and coordinates a bounded system.
- Resolver: calculates an outcome without presenting it.
- Executor: performs an ordered action/command plan.
- Request: represents an attempted action that has not yet been approved.
- Gate: answers one specific permission question without changing state.
- Validator: evaluates validity when Gate is not the appropriate architectural term.
- Command: represents an approved operation.
- Fact: structured data describing a completed authoritative change.
- View: Unity scene/prefab presentation and input surface.
- Presenter: converts state/events into a view instruction when a separate object is useful.
- Repository or Catalog: resolves stable IDs to definitions.
- SaveData: serialized persistence representation.


Avoid using Manager for every object. A Manager name is allowed only when the object genuinely coordinates a broad lifecycle and no narrower responsibility name is clearer.


DICE TERMINOLOGY IN CODE
Use Dice consistently in type and member names, including when one gameplay object is being discussed, unless Elise later approves a different code convention. Examples: DiceDefinition, DiceRuntimeState, DiceView, selectedDice, activeDiceId, IReadOnlyList<DiceRuntimeState> dice.


The glossary remains the authority for communication terminology even if a future code-name exception is approved.


SLOT IDS
- Human/document label: 1E through 6E and 1P through 6P.
- Public/runtime identity: Side plus a one-based logical Number from 1 through 6.
- Internal arrays and lists use zero-based storage indexes from 0 through 5.
- Convert between SlotId.Number and a storage index only through one shared conversion helper.
- Gameplay code must not perform scattered manual +1 or -1 conversions.
- Never infer a slot from its GameObject name during play.


Example reference shape, not final code:


public enum Side { Enemy, Player }
public enum SlotCondition { Unbroken, Unstable, Broken }
public enum BattlePhase
{
    Setup,
    Rolling,
    EnemyReposition,
    PlayerReposition,
    DecayProcess,
    ScoreProcess,
    RoundEnd,
    GameEnd,
    BattleEnd
}


public readonly struct SlotId
{
    public Side Side { get; }
    public int Number { get; }

    public SlotId(Side side, int number)
    {
        Side = side;
        Number = number;
    }
}






STABLE IDS
Persistent identity must not depend on display names, asset filenames, GameObject names, scene placement, or collection position.

Definition IDs identify authored content and use a lowercase category.name pattern:
- dice.clockwork
- dice.blessed
- charm.red_checker
- enemy.tutorial_dealer

Every owned Dice receives a mandatory automatically generated unique instance ID separate from its definition ID. Fields and properties that contain an identity end in Id, such as definitionId, instanceId, or slotId.


OPERATION TYPE NAMES
Names for gameplay operations must state what type of operation they represent. Do not use a generic root such as PhaseChange or DiceMove for several unrelated responsibilities.

Examples:
- Attempted action: MoveDiceRequest or PhaseChangeRequest.
- Permission check: DiceMovementGate or PhaseTransitionValidator.
- Approved operation: MoveDiceCommand or ChangePhaseCommand.
- Completed structured result: DiceMovedFact or PhaseChangedFact.
- Ordinary event raised after completion: DiceMoved or PhaseChanged.


ASSET NAMES
Use predictable descriptive names. Use prefixes to declare what TYPE of object or code is presented, then describe what it does or is attached to, and then any other details
Suggested patterns:
- Dice definition: def_DICE_Clockwork
- Charm definition: def_CHARM_RedChecker
- Enemy definition: def_ENEMY_TutorialDealer
- Battle config: conf_BATTLE_Tutorial_01
- Tutorial plan: plan_TUTORIAL_IntroBattle
- Prefab: PF_DiceView, PF_SlotView
- Animation clip: ANIM_Dice_Roll, ANIM_Slot_Decay
- Animator controller: AC_Dice, AC_Hourglass
- Sprite: SPR_Hourglass_Roll, SPR_Hourglass_Decay
- Material: M_Table_Unlit
- Sound: SFX_Dice_Roll, SFX_Slot_Break


GameObject names should describe scene role: Slot_1E, Slot_1P, DiceViewRoot, PlayerDrawer, EnemyDialogueAnchor.


SERIALIZED FIELDS
Prefer private serialized fields over public mutable fields:


[SerializeField] private DiceDefinition _definition;
[SerializeField] private Animator _animator;


Expose read-only properties or explicit methods when another object needs access.


C# FILE AND MEMBER NAMES
- A script filename must match its primary type name.
- Use one primary public type per file.
- Collections use plural names, such as dice, slotStates, or pendingCommands.
- Identity variables end in Id, such as definitionId, instanceId, or slotId.
- Methods use specific action names, such as RequestMove, ResolveRound, or PlayDecay.
- Do not use vague names such as HandleData, ProcessThing, DoAction, UpdateStuff, Helper, or Utils.
